# #279 おまけ（ご褒美）を支払いと一緒に渡す — 設計メモ（2026-11-08 brainstorming）

出典: issue #279 のコメント（<https://github.com/es0612/OtetsudaiCoin/issues/279#issuecomment-6714358992>）を 2026-11-08 に転記。正本は issue 側

ステータス: idea（設計の方向を記録。実装は未着手）

## 目的（オーナーの言葉と回答から）

- 実際のお小遣いは、お手伝いの記録の額より多めに渡すことがある。「頑張ったね」と褒めて、おまけを付ける（issue 本文）
- おまけを付けるのは「**特に頑張ったことを褒めて上乗せ**」する場面（2026-11-08 の回答）
- 子どもに見えてほしいもの（回答・複数）: ①**渡すその場の演出**（褒め言葉とおまけの額）、②**後で見返せる記録**（月のまとめ・履歴に残る）

## ゴール

1. 月のお小遣いを支払うときに、おまけ（額 + 褒め言葉スタンプ 1 つ）を**任意で**足せる
2. 支払いを確定した瞬間に、選んだスタンプとおまけの額が大きく出る演出がある
3. その子の月のまとめ（と履歴）で、後から「どの月に・どのスタンプで・いくら」のおまけをもらったかが見える

## 非ゴール

- 支払いとは別のタイミングでおまけだけを渡す（入れる場面は「支払うときに一緒に」を選んだ）
- 理由の自由入力（入れ方は「褒め言葉のスタンプ」を選んだ）
- スタンプの文言を親が編集・追加する（v1 は固定セット。Claude の判断）

## アンチゴール（これが起きたら作らない方がよかった、の回答）

- **支払いが面倒になる**: おまけを付けない月の操作は、今と同じ「ボタンを 1 回押すだけ」から増やさない
- **兄弟で比べて不公平感**: 子ども同士のおまけを並べて見せない。おまけはその子の画面（月のまとめ・履歴・支払い時の演出）にだけ出し、ホームの子ども一覧のような複数の子が並ぶ場所には出さない

## 制約（main 7fab0b2 のコードで確かめた事実）

- **画面から呼ばれている支払いの入口は 1 つだけ**: 月のまとめの CTA「この月のお小遣いを支払う / 追加分のお小遣いを支払う」（`MonthlySummaryView.swift:205-218`）→ `MonthlySummaryViewModel.payCurrentMonth()`（`:96`）。**確認画面はなく、押すと即座に支払う**
- ホームの `HomeViewModel.payMonthlyAllowance()` / `recordAllowancePayment(amount:)`（`:195, :207`）はテストからしか呼ばれていない（View の呼び出し 0 件）。今回は触らない（残す・消すは別 issue で判断）
- 支払い状態は、その月の `AllowancePayment.amount` の合計と稼いだコインの比較で決まる（`MonthlySummaryViewModel.computePaymentStatus` `:242-257`）。CTA の額は `totalCoins - paidAmount`（`MonthlySummaryView.swift:206`）
  - → **おまけを `amount` に混ぜない**。混ぜると、払った額の合計が稼いだ額を超え、「残額」と「払った額」の表示が崩れる可能性が高い（推測、未検証）。おまけは別の値として持つ
- `AllowancePayment.note` は ViewModel が決まった文（「2026年11月のお小遣い支払い」など）を書いている（`MonthlySummaryViewModel.swift:112`）。親が入力する場所はない。スタンプを `note` に入れると、この文と混ざるので使わない
- 永続化は Core Data（`OtetsudaiCoin.xcdatamodeld` は 4 版まである）。属性を足すなら新しいモデル版 + 軽量マイグレーション。既存の支払い行は「おまけなし」として読めること
- 金額の表記は「¥」と「コイン」が混在している（#155 で表記ルールを決める予定）。おまけの表記は CTA と同じ「¥」に揃え、#155 で一緒に見直す（Claude の判断）

## 作る人に任せること（Claude の判断として記録）

- **おまけを付けられるのは、支払う額が残っている月だけ**（2 つ目の入口は CTA と同じ条件 `paymentStatus != .paid` で出す）。払い終えた月に後から足す・稼ぎ 0 の月に励ましとして付ける、は v1 の非ゴール。「支払うときに一緒に」の回答をそのまま読んだ。要るなら別 issue（`amount` 0 の行・`computePaymentStatus` / `UnpaidAllowanceDetectorService.swift:31` の判定への影響を含む）
- 2 つ目の入口の見た目は CTA より目立たない副ボタン / テキストリンク（おまけなしの支払いを主役のまま保つ）

- スタンプの初期セット（例: 「がんばったで賞」「ありがとう賞」「まいにちコツコツ賞」「チャレンジ賞」の 4〜6 個、絵文字付き。ja / en の xcstrings を用意）
- おまけの額の入れ方（例: +10 / +50 / +100 のチップと、数字の直接入力）。上限は設けない
- データの持ち方（`AllowancePayment` に `bonusAmount: Int`（既定 0）と `bonusStampKey: String?` を足す / 別エンティティにする、のどちらか）。月のまとめで「稼いだ分」と「おまけ」を分けて出せること
- 演出の見た目（#278 トンマナの検討と合わせてよい）
- 「視差効果を減らす」が ON のときは、演出の動きをフェードに置き換える（#151 の方針と同じ）

## 物差し（案）

- おまけを付けない支払いのタップ数が今と同じ（1 回）であること（UI テストで担保）
- 実装後 1 か月、オーナーの家庭でおまけを付けた月に、アプリの「払った額」と実際に渡した額が一致しているか（手で確かめる）
